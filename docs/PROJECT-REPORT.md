# After 방과후 수업 제안 및 운영 프로젝트 보고서

**기준일** 2026년 11월 26일 · **대상** `After-fe` 프런트엔드와 `After-BE` 백엔드의 로컬 변경사항

## 1. 프로젝트 개요

After는 학생이 원하는 방과후 수업을 제안하고, 학교 선생님과 학생이 운영 시간을 정한 뒤, 학교가 지정한 날에 수강신청을 진행하는 서비스다. 이번 작업에서는 제안이 공개되는 시점, 선생님이 투표를 시작하고 마감하는 권한, 수강신청 화면이 열리는 조건을 연결했다.

학생은 제안과 일정 투표에 참여하고, 학교 선생님은 제안을 맡아 투표 결과를 바탕으로 개설을 확정한다. 학교관리자는 학기, 제안 접수 기간, 가입 코드와 계정 승인을 관리한다.

## 2. 수업이 개설되는 과정

| 단계 | 사용자 동작과 시스템 처리 |
| --- | --- |
| 제안 등록과 수요조사 | 학생이 새 제안을 올리면 즉시 **수요조사중**으로 공개된다. 관심은 0명에서 시작하고 작성자 본인은 관심을 표시할 수 없다. 작성자는 투표가 열리기 전까지 제안 내용을 수정하거나 제안을 철회할 수 있다. |
| 선생님 수락 | 선생님이 **월요일 8교시~10교시**, **수요일 8교시~10교시** 중 후보를 선택하고 투표 마감 시각을 정한다. 수락과 동시에 **일정투표중**으로 전환되며, 관심 인원수나 사전 관심 응답에 관계없이 대상 학년 학생 전체가 참여할 수 있다. |
| 일정 투표와 마감 | 학생은 각 후보에 대해 가능, 조정 가능, 불가능으로 응답한다. 담당 선생님은 예정 시각보다 일찍 마감할 수 있다. 조기 마감 시 기존 응답은 유지되고 새 응답은 차단된다. |
| 개설 확정 | 투표가 끝나면 담당 선생님이 응답 결과를 보고 후보 중 한 시간을 확정한다. 수업의 담당 선생님, 운영 시간, 수업 설명을 개설 확정 목록에서 확인할 수 있다. |
| 공통 수강신청 | 학교가 정한 날짜에는 한국 시간 00:00부터 다음 날 00:00 직전까지 신청 화면이 열린다. 기간 밖에는 잠금 안내와 개설 확정 목록 링크가 표시된다. 학생의 신청과 취소 가능 기간은 서버에서도 검사한다. |

## 3. 화면과 사용자 경험 개선

- **수업 제안 목록**은 수요조사 중이거나 일정 투표 중인 제안만 보여준다. 직접 작성한 제안은 목록과 상세에서 **내 제안**으로 표시한다. 관심이 0명일 때도 빈 진행 바를 표시하고, 새 제안은 희망 정원을 기준으로 바를 채운다.
- **제안 상세**의 수정·삭제는 작성자에게 제공한다. 투표가 시작되면 이미 열어 둔 수정 화면에서도 저장할 수 없다. 삭제한 제안은 학생과 교사 목록에서 내려가고 서버에는 철회 이력이 남는다.
- **새 수업 제안**은 기본 정보, 수업 내용, 강사 추천을 구분했다. 입력 글씨는 16px, 플레이스홀더는 15px로 조정했다. **제안 올리기**와 **나가기**는 넓은 화면에서 기본 정보 오른쪽에 두고, 좁은 화면에서는 입력 영역 아래에 표시한다.
- **일정 투표 화면**은 응답 개수를 표시하고, 제출 버튼 위의 진행 바를 제거했다. 수업 제안 상세의 **일정 투표하기** 버튼 정렬도 수정했다.
- **개설 확정 수업**은 한 줄에 한 수업씩 표시해 수업명과 설명, 운영 시간과 담당 선생님을 비교할 수 있게 했다. 수강신청 여부와 별개로 접근할 수 있는 화면이며, 목록의 공통 배지는 신청 기간에 맞춰 **개설확정** 또는 **수강신청중**으로 표시된다.

## 4. 기술 구성과 연동

프런트엔드는 React와 Vite로 구성했다. 체험 모드에서는 브라우저에 데이터를 저장해 학생·선생님 흐름을 확인할 수 있다. API 모드는 `VITE_DATA_MODE=api`와 `VITE_API_BASE_URL`을 사용해 FastAPI 서버의 `/api/v1`에 연결하며, 로그인은 HttpOnly 쿠키를 사용한다. 백엔드는 PostgreSQL에 제안과 응답을 저장하고, Redis와 ARQ 워커로 마감 처리와 알림 등의 작업을 수행한다.

학생 화면은 `/`, 선생님 화면은 `/teacher`, 개설 확정 목록은 `/courses`, 수강신청은 `/enrollments`에서 접근한다. 투표 대상 학년, 작성자 권한, 담당 선생님 권한, 마감 시각은 서버에서 검사한다. [프런트엔드 실행 안내](../README.md) · [API 연동 계약](API-CONTRACT.md) · [백엔드 연동 사항](BACKEND-FOLLOWUP.md)

검증 결과는 로컬 빌드와 자동 테스트 기준이다. 실제 학교 환경의 배포와 브라우저에서의 전체 연동은 별도 검증이 필요하다.

## 6. 운영 전 남은 작업

1. **신규 DB 마이그레이션 검증**. 백엔드 `main`의 초기 마이그레이션에서 `time_slots`를 생성하고 후속 `0002_weekday_blocks`에서 `end_period` 열을 추가한다. 로컬의 미커밋 `0001_initial` 변경까지 적용하면 같은 열을 두 번 추가하게 된다. 초기 설치 경로와 기존 DB 업그레이드 경로를 PostgreSQL에서 각각 검증해야 한다.
2. **회원가입 요청 형식 일치**. 프런트엔드 가입 폼에서 `passwordConfirm`이 빠져 있고, 학번·반·알림 동의 필드 이름도 서버와 다르다. 요청 형식을 맞추고 학생·선생님 가입과 관리자 승인까지 확인해야 한다.
3. **학교 일정과 강좌 노출 정책 확인**. 학기와 제안 접수 기간을 등록하고, 강좌 확정 전에 프런트엔드 `VITE_ENROLLMENT_DATE`와 백엔드 `SCHOOL_ENROLLMENT_DATE`에 같은 날짜를 설정한다. 신청 마감 후 서버에서 `RUNNING` 또는 `CLOSED`로 전환된 강좌를 개설 확정 목록에 계속 보여줄지 정해야 한다. 현재 학생 목록 API는 `CONFIRMED`와 `ENROLLING`만 반환한다.
4. **배포 환경 통합 검증**. PostgreSQL 마이그레이션과 동시 신청 테스트를 실행하고, 실제 브라우저에서 로그인 쿠키, 제안 등록, 투표, 수강신청까지 확인한다. 현재 보고 범위에는 두 저장소의 미커밋 변경사항이 포함되어 있다.
